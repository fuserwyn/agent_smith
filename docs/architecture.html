Архитектура Agent Smith

Агент получает задачу и решает её сам: думает, пишет Python-код, запускает его в песочнице, смотрит вывод и повторяет, пока не вызовет final_answer(). Ниже схема всех частей, зоны доверия между ними и описание каждого блока.

Схема системы

Пунктирные рамки — границы процессов. Пунктирные стрелки пересекают границу: сеть, pipe, stdio или docker exec. Нажмите на блок, чтобы прочитать его описание.

На узком экране схему можно прокрутить вбок.

    Что делает каждый блок и как он работает внутри. Сгруппировано по зонам доверия, как на схеме.

    Почему устроено именно так

    Код модели исполняется в отдельном процессеЗависший код можно убить по таймауту, лимит памяти через setrlimit не задевает агента, а падение worker не роняет цикл.
    MCP-клиент живёт в родителе, в worker только проксиУ недоверенного кода нет сокетов. MCP-вызовы идут вне таймаута песочницы, как требует сабжект.
    Worker живёт всю задачуПеременные сохраняются между шагами: модель может найти файл на одном шаге и использовать результат на следующем.
    Любой формат вызова тулов становится PythonПесочнице всё равно, какая модель ответила: XML, JSON или ReAct переводятся в обычные вызовы функций.
    Тулы берутся только из list_tools()На защите подключат чужой MCP-сервер. Мануал для промпта строится из его схем без правок кода.
    Слои не знают друг о другеЛогика тулов не знает про MCP, сервер не знает про агента, цикл не знает про провайдера. Каждый слой тестируется отдельно.
